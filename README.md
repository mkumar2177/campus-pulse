# Campus Pulse

Campus Pulse is a Flutter + Serverpod + PostgreSQL campus discovery app for BUILD ROYALE 2026.

> The supplied presentation describes illustrative mockups and proposed 50/30/20 matching weights. This repository implements the matching calculation and labels seeded records as demo data; no score is presented as a validated research result.

## Status

The project includes a deterministic local demo repository so the core judging flow remains usable before PostgreSQL is configured. The current Flutter client now includes login/sign-up validation, event discovery and registration, bookmarks, profile editing, student directory search, connection requests, notifications, and a local conversation composer. The Serverpod service remains the production persistence boundary; the new social features still require Serverpod models/endpoints before they are shared across devices.

## Prerequisites

- Flutter stable and Dart from the same Flutter installation
- Dart `serverpod_cli` 2.9.5 (or the matching Serverpod release)
- PostgreSQL 14+

The repository pins Serverpod 2.9.5-compatible packages. Run `flutter pub get`
and `serverpod generate` after installing the listed tools.

## Run locally

```powershell
# From server/
serverpod generate
docker compose -f docker-compose.yml up -d
serverpod create-migration -t initial
dart pub get
dart bin/main.dart --mode development --apply-migrations
# Apply the generated migration, then seed demo records:
docker compose exec -T postgres psql -U postgres -d campus_pulse < scripts/seed.sql

# From app/
flutter pub get
flutter run
```

For a physical Android device, replace `localhost` in `app/lib/config/app_config.dart` with the laptop's LAN address and allow the Serverpod port through the firewall. The local demo repository works without a network connection and is explicitly labelled in the UI.

## Demo accounts

The local demo uses:

- Student: `student@campuspulse.demo` / `DemoStudent123!`
- Organizer: `organizer@campuspulse.demo` / `DemoOrganizer123!`

These are demo-only credentials. Production authentication must be backed by Serverpod's auth/session implementation and environment-managed secrets.

## Judge flow

1. Open the app and continue as the demo student.
2. Edit interests, goal, and availability from Profile.
3. Search or filter the Feed, open Campus Hack Night, bookmark it, and register.
4. Open Buddies, inspect the score breakdown, and send a match request.
5. Use the organizer workspace entry from Profile to inspect seeded registrations.
6. Use **Reset demo data** in Settings to repeat the flow. The app attempts the generated Serverpod feed endpoint first and keeps bookmarks, registrations, profile, and session in the local demo store when the backend is unavailable.

## Architecture

- `app/lib/domain`: typed entities and matching rules.
- `app/lib/data`: repository contract and deterministic local repository.
- `app/lib/presentation`: reusable theme, navigation, and screens.
- `server/lib/src`: Serverpod endpoints and service boundary.
- `server/migrations`: PostgreSQL migration generated by Serverpod.
- `client/lib/src/protocol`: generated typed Serverpod Flutter client protocol.

## Known limitations

- The app attempts the generated Serverpod event endpoint first and visibly falls back to deterministic local demo data when the backend is unavailable.
- Local sign-up, connections, notifications, and messages are demo-local state. They are intentionally not presented as server-backed real-time chat or production authentication.
- Authentication, organizer authorization, PostgreSQL transactions, and WebSocket delivery belong to the Serverpod service integration step; the demo UI does not claim those checks are server-enforced yet.
- Attendance check-in is a future enhancement and is not exposed as a working feature.
